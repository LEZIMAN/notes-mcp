# 意图过滤模型选型报告

> 背景:检索层(rerank)解决排序,但无关/歧义 query 仍走完整流程浪费 token(云端主模型场景)。
> 加轻量意图过滤:模型粗判 normal/irrelevant/ambiguous,挡无关省云端调用。
> 本报告实测三模型,选型 **qwen3:8b + think:false**。2026-07-26

---

## 背景

rerank 提升了头部精度(recall@1 57.8→71.1%),但无法判断"query 该不该回答"——
无关 query(红烧肉)和歧义 query(术语堆砌)仍会触发检索+主模型生成,浪费云端 token。

加意图过滤层(云端主模型场景):
- **irrelevant**(红烧肉/天气)→ 直接拒答,不走云端主模型(省 token)
- **normal**(什么是 RAG)→ 检索 + rerank + 主模型
- **ambiguous**(术语堆砌)→ 主模型三态路由兜底(提示细化)

---

## 选型标准

- **中文理解**:query 多中文
- **轻量快速**:粗判 <2s(不阻塞主流程)
- **指令遵循**:能按 prompt 输出分类标签
- **Ollama 可用**:项目已用 ollama,小模型层走本地(免费)

---

## 实测

### 测试集(8 条 query)

| query | 期望 | 说明 |
|---|---|---|
| 什么是 RAG | normal | 明确问题 |
| qwen3 本地部署 | normal | 短技术 query(有意图) |
| ReAct 和 Reflexion 区别 | normal | 对比问题 |
| 红烧肉怎么做 | irrelevant | 完全无关(菜谱) |
| 英超联赛积分榜 | irrelevant | 无关(体育,但像数据查询) |
| 北京明天会下雨吗 | irrelevant | 无关(天气,有疑问但领域外) |
| Transformer RAG LangGraph ollama | ambiguous | 术语堆砌 |
| MCP Token Embedding | ambiguous | 术语堆砌(最难,和正常短 query 像) |

### 结果对比

| 模型 | prompt | 准确率 | 速度/query | ambiguous | 备注 |
|---|---|---|---|---|---|
| qwen2.5-coder:3b | v1(简短) | 4/5 | — | — | 只测 5 条 |
| qwen2.5-coder:3b | v2(领域感知) | 2/8 | — | — | ❌ 长 prompt 抖动 |
| qwen3:1.7b | v2 | 5/8 | ~2-3s | 0/2 | ambiguous 全错 |
| qwen3:8b | `/no_think`(prompt) | 7/8 | **14.5s** ❌ | 1/2 | thinking 没关(坑 #25) |
| **qwen3:8b** | **`think:false`(API)** | **7/8** | **0.6s** ✅ | **1/2** | **选定** |

### 详细数据(qwen3:8b + think:false,7/8)

```
✓ 什么是RAG (normal)              [0.9s]
✓ 红烧肉怎么做 (irrelevant)       [0.6s]
✓ Transformer RAG LangGraph (amb) [0.5s]   ← 1.7b 判错,8b 对
✓ qwen3 本地部署 (normal)         [0.5s]
✓ 英超联赛积分榜 (irrelevant)     [0.6s]   ← 1.7b 判错,8b 对
✓ 北京明天会下雨吗 (irrelevant)   [0.6s]   ← 1.7b 判错,8b 对
✓ ReAct 和 Reflexion 区别 (normal)[0.5s]
✗ MCP Token Embedding (amb→normal)[0.6s]   ← 唯一错(最难,交主模型兜底)
```

---

## 结论:qwen3:8b + think:false

| 维度 | 表现 |
|---|---|
| 准确率 | 7/8 (87.5%)——三模型最高 |
| 速度 | 0.6s/query——比 1.7b 还快(GPU + 关 thinking) |
| ambiguous | 1/2——比 1.7b(0/2)强,难例交主模型兜底 |
| 复用 | 主模型 qwen3:8b,不额外装小模型(省 1.5GB) |
| 本地免费 | 小模型层永远走本地 ollama,不增云端成本 |

### 为什么 8b 比 1.7b 快?

反直觉但合理:8b 是主模型常驻内存(GPU 已加载),1.7b 反而要冷启动加载;加上 `think:false` 关掉 thinking,8b 生成一个分类词极快(0.6s)。**"模型小=快"在此不成立**(常驻 + think:false 才是关键)。

---

## 关键坑:`/no_think` 对 qwen3 ollama 无效

```
/no_think(prompt 指令) → ollama 仍开 thinking → 14.5s ❌
think:false(API 参数)  → 真关 thinking         → 0.6s ✅
```

qwen3 的 thinking 是**引擎层开关**,prompt 级 `/no_think` 关不掉。详见 [踩坑 #25](./踩坑记录.md)。

---

## 架构(选定后)

```
query → [qwen3:8b think:false 粗判] 0.6s,本地免费
         ├─ irrelevant → 拒答"笔记里没有",不走云端主模型(省 token)
         ├─ ambiguous → 主模型三态路由兜底(提示细化)
         └─ normal    → 检索(粗召回20→rerank→top5)→ 主模型回答
```

- **粗判层**(qwen3:8b think:false):挡 obvious irrelevant,省云端 token
- **主模型三态路由**:兜底漏网无关 + 识别 ambiguous(粗判做不了的)

---

## 启示

1. **选型必须实测**,不能凭"8b 慢"的直觉——think:false 后 0.6s,颠覆假设。
2. **关 thinking 是 qwen3 性能关键**——简单任务(分类/判断)必关,复杂推理才开。
3. **模型大小≠速度**——常驻 + think:false 比"换小模型"更有效。
4. **ambiguous 最难分类**——术语堆砌 vs 正常短 query,小模型分不清;交主模型兜底更稳。
