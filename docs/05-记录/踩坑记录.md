## 🛠 scripts/dev.py

### 5. `test` 子命令 `-q` 透传失败(argparse 局限)
- **现象**:`dev.py test -q` 报 `unrecognized arguments: -q`。试过 `nargs="*"` 和 `nargs=REMAINDER` 都不行。
- **根因**:argparse 把 `-` 开头的参数当 option 解析,找不到 `-q` 选项就报错;`REMAINDER` 对子命令首个 `-` 参数仍不可靠。
- **修复**:`main()` 里对 `test` 子命令**特判**——`if argv[0]=="test": return cmd_test(argv[1:])`,绕开 argparse,原样透传给 pytest。
- **启示**:argparse 的"透传未知参数"是已知坑,对 wrapper 脚本特判最稳。

### 6. E501 行长超 100(`add_parser` 链式)
- **现象**:逐行 `sub.add_parser(...).set_defaults(...)` 多行超 100 字符。
- **修复**:用注册表 + 循环批量注册,既短又 DRY。

## ✂️ chunker

### 7. 滑动窗口切块的边界(测试预期错)
- **现象**:`_split_text("0123456789", size=5, overlap=2)` 预期 3 块,实际 4 块。
- **根因**:step=3 时 `[0:5][3:8][6:10]` 后,`pos=9 < len=10` 还会切 `[9:10]="9"` 一块。**这是滑动窗口的正确行为**,不是 bug——是测试预期写错了。
- **修复**:改测试预期为 4 块。
- **启示**:先确认是"代码错"还是"理解错",别急着改实现。

## 📦 indexer

### 8. Path/str key 混用导致增量建库失效(致命 bug)⚠️
- **现象**:首次建库正常,但第二次 build 把所有文件当"新增+删除"(增量完全失效)。
- **根因**:`_scan` 返回 `dict[Path, float]`,`_load_db` 返回 `dict[str, FileState]`。`_diff` 里 `set(disk) - set(db)` 是 `set[Path] - set[str]`——**Path 和 str 永不相等**,集合运算认为完全不重叠 → 每次全量新增 + 全量删除。
- **修复**:内部 key **统一用 `str(path.resolve())`**(SQLite 天然存 str),`_scan`/`_load_db`/`_diff`/`_sync_sqlite` 全程 str,需要 Path 处再 `Path(path)`。
- **启示**:跨边界的 key 类型必须统一。mypy 能抓一部分(返回类型注解不符),但运行时 set 运算的隐式类型不匹配 mypy 不一定报。

### 9. bm25s 0.3.9 API:`save` 从模块函数变实例方法
- **现象**:`bm25s.save(retriever, dir)` 报 `module 'bm25s' has no attribute 'save'`。
- **根因**:bm25s 0.3+ 把 `save` 从模块级函数改成了 `BM25` 实例方法(`retriever.save(dir)`),`load` 仍是类方法。
- **修复**:`self._bm25.save(str(dir))`;装新依赖后先 `dir(bm25s)` / `dir(BM25)` 探测实际 API,别凭记忆。

### 10. Chroma `EphemeralClient` 同进程共享 + 固定 collection 名累积
- **现象**:`test_stats_resource` 断言 `total_files==3`,实际 `18`。
- **根因**:`chromadb.EphemeralClient()` 在**同进程内共享内存**,`get_or_create_collection("固定名")` 跨测试复用同一 collection,每次 fixture build 3 篇 → 累积(6 次测试 = 18 distinct sources,因 tmp_path 不同)。
- **修复**:测试 fixture 的 collection 名用 `tmp_path.name` 后缀(`f"server_{tmp_path.name}"`),保证每次唯一隔离。
- **启示**:EphemeralClient 不是"每次新内存",而是进程级共享。测试隔离要靠唯一命名,不能靠"新建 client"。

### 11. Searcher 缺 `collection` property
- **现象**:server 用 `searcher.collection` 报 `'Searcher' has no attribute 'collection'`。

### 12. fastmcp `read_resource` 返回 `list`(非对象)
- **现象**:`_resource_text` 用 `getattr(result, "contents")` 取不到,`json.loads` 失败。
- **根因**:fastmcp 3.x 的 `Client.read_resource` 直接返回 `list[TextResourceContents]`,不是带 `.contents` 的对象。
- **修复**:先判 `isinstance(result, list)`;第三方库返回结构别假设,先 `type(result)` / `dir(result)` 探测。

## ⚡ 性能

### 13. 建库慢(~5 分钟 / 1052 chunks)
- **现象**:首次 `index` 建 1052 chunk 耗时 ~5 分钟。
- **根因**:`OllamaEmbedder.embed` 是**单条**,indexer 循环 1052 次,每次一次 HTTP 往返(0.3s)。往返开销 × 1052 ≈ 5 分钟。
- **待优化**:加 `embed_batch(texts)` 批量嵌入(ollama `/v1/embeddings` 支持一次多 input),indexer 单文件 chunk 一次 embed。预期 1052/64 ≈ 17 次请求 → ~30 秒。
- **启示**:逐条 HTTP 是性能杀手;批量 + 摊薄往返开销是首选优化。

## 🌐 Web 后端(Phase 3a · Spring Boot)

### 16. Spring AI 连 fastmcp:相对路径 + 子进程 cwd 致 initialize 超时(多层排查)
- **现象**:Spring Boot(Spring AI MCP client stdio)启动 `Client failed to initialize`,20s 超时。手动测 fastmcp 响应 initialize **完全正常**。
- **根因**(层层剥):
  1. mcp-core(Java)spawn notes-mcp 子进程的 **`cwd` 配置字段没生效**(子进程实际 cwd = Java 进程 cwd,非项目根)。
  2. notes-mcp 的 `CHROMA_PATH=./data/chroma` 是**相对路径**,cwd 一变 → data 落到别处 → 触发**全量重建库**(embed 1052 chunk ~60s)。
  3. 子进程建库未完成 → mcp-core initialize 等不到响应 → 20s 超时。早期还叠了「`No module named notes_mcp`」(cwd 错导致 import 失败)和「streamable-http 跨实现互操作」两个干扰项。
- **修复**(组合拳):
  - `pip install -e .` 把 notes_mcp 装进 venv → 子进程任意 cwd 都能 import。
  - Config 加 `_resolve_path`:相对路径基于项目根解析 → data 永远指向已建库,不依赖 cwd。
  - Spring AI spawn args 加 `-u`(Python stdout 无缓冲,防父进程读不到)。
- **启示**:跨语言/跨进程 spawn 子进程时三件事——① **不依赖 cwd**(路径绝对化或包安装进环境);② **stdout 无缓冲**(否则父进程读不到响应);③ 先抓子进程 **STDERR** 确认它真的启动了(别只看父进程的笼统异常)。

## 🌐 多 Provider(Phase 3b · Settings)

### 18. OpenAiChatOptions.apiKey() 不覆盖自动配置的密钥
- **现象**:切换到 DeepSeek Provider 后对话报 `401: Incorrect API key provided: unused`。明明 settings.json 里配了正确的 API key,但实际请求用的是 application.yml 里占位的 `unused`。
- **根因**:Spring AI 2.0.0 自动配置的 `OpenAiChatModel` 内部已有 `OpenAIClient`(用 `unused` 创建)。`ChatClient.prompt().options(OpenAiChatOptions.builder().apiKey(...))` 的 options 只是请求级参数,**不会覆盖底层 HTTP client 的认证凭据**。
- **修复**:不用自动配置的 `OpenAiChatModel`,改用 `OpenAiChatModel.builder().options(opts).build()` 动态创建,让 Spring AI 从 options 里读取 apiKey/baseUrl 构建新的内部 client。ProviderRouter 加缓存,同配置复用。
- **启示**:Spring AI 的 ChatOptions.apiKey() 设计上是用于「创建新 Model 时指定凭据」,不是「运行时覆盖已有 Model 的凭据」。多租户/多 Provider 场景需动态创建 ChatModel,不能依赖自动配置的单例。

### 19. 自定义 Provider 模型列表为空
- **现象**:切换到 DeepSeek 自定义 Provider 后,模型列表返回 `[]`,用户无法选择模型。
- **根因**:部分第三方 API(如 DeepSeek)不提供 `/v1/models` 端点,或端点路径不同。Spring AI 通过 OpenAI Java SDK 调 `/models` 拿不到数据。
- **修复**:前端模型管理 Tab 增加**手动输入模型名**功能——API 返回空列表时,显示文本框让用户直接输入模型 ID(如 `deepseek-chat`),回车或点击即可使用。

### 20. MCP client initialize 超时(坑 #16 的同源复发)⚠️
- **现象**:后端启动报 `Client failed to initialize by explicit API call`,Bean 创建失败,应用起不来。时间线:MCP server started(30s)→ BM25 恢复(44s,耗时 14s)→ initialize 失败(50s,正好 20s 窗口)。
- **根因**:Spring AI MCP client 默认 `requestTimeout`(≈20s)覆盖 initialize 请求。notes-mcp 子进程首次启动时,BM25 恢复(14s)+ 后续 indexer 增量扫描(_scan 扫目录 + _diff)加起来超过 20s 窗口。**笔记增多到 31 篇 1297 chunks 后,BM25 恢复变慢,正好踩穿之前没暴露的阈值**——和坑 #16 同根(都是子进程启动慢导致父进程超时),只是这次超时发生在 initialize 握手阶段,不是数据加载阶段。
- **修复**:`application.yml` 加 `spring.ai.mcp.client.request-timeout: 120s`,给 initialize 充足窗口。
- **启示**:跨进程 spawn 的「父进程超时 vs 子进程冷启动耗时」是反复出现的隐患——① 坑 #16 治了路径/缓冲;② 这次治了握手超时。**笔记库越大,BM25 恢复越慢,默认 20s 迟早不够**。超时配置应一开始就显式设大,别等踩雷。子进程冷启动的耗时项要心中有数(embed 模型加载 / BM25 反序列化 / 目录扫描),任一项变慢都可能击穿默认超时。

## 📊 检索 eval(P0)

### 21. Chroma `collection.get(ids=...)` 返回顺序不保证,eval 算出假 recall ⚠️
- **现象**:写检索 eval 算 recall@k 时,发现「无权重 RRF 与加权 0.5:0.5 结果不同」(数学上两者等比缩放、排序必相同)、「扫不同 RRF k 值结果完全一样」——明显违背数学,数据不可信。
- **根因**:`collection.get(ids=chunk_ids)` 返回的 `metadatas` **顺序不保证与入参 ids 一致**(Chroma 内部按 hash 顺序返回)。eval 脚本直接遍历返回的 metadatas 拼成 source 列表 → 这个列表是**乱序**的,recall@k 算的"前 k"其实是 Chroma 随机返回的前 k,不是 RRF 排名前 k。乱序导致:不同 k 值结果相同(顺序与 k 无关)、不同方法结果随机差异。
- **修复**:`ids_to_sources` 先建 `id→source` 映射,再**按入参 chunk_ids 顺序**取(保留排名顺序),而非按 Chroma 返回顺序。
- **启示**:① 任何依赖「按指定 id 顺序取数据」的逻辑,都不能信向量库返回顺序,必须自己用映射重排;② 生产代码 `search.py:_build_hits` 早年就做了 `id_to_meta` 映射重排(坑 #8 时期养成),所以**线上检索排序是对的,只有 eval 脚本中招**;③ eval 数据"看起来合理"时也要警惕——若出现违背数学的怪象(等价操作结果不同),八成是中间有个隐藏的顺序/状态依赖。

### 22. RRF 融合在「强语义 + 弱 BM25」数据集上是负优化(eval 实证)⚠️
- **现象**:eval 跑出真实数据后,Hybrid(RRF) 不仅没提升 recall,**MRR 和 recall@1 反而低于纯语义**:语义 recall@1=68%/MRR=0.798,Hybrid recall@1=44%/MRR=0.638。
- **根因**:bge-m3 语义检索在此笔记库已极强(recall@5=100%),RRF **没有 recall 提升空间**;而 BM25 偏弱(recall@5=76%,中文分词后同板块笔记词频高、噪声大)。无权重 RRF 把弱路的"同板块沾边 chunk"与语义命中 chunk 等权对待,凭 id 字典序把语义的头部命中挤到 rank2-3 → 头部精确度(recall@1)和排序质量(MRR)双降。加权诊断证实:越偏向语义,MRR 越接近纯语义(0.9:0.1 → MRR 0.690 > 无权重 0.638)。
- **修复/方向**:短期给 RRF 加可配权重(偏语义);根本解法是 **rerank**(P1:RRF 出 top-20 候选 → bge-reranker 精排 top-5,救 MRR)。RRF 真正的用武之地是"两路各有独占命中"的互补场景,当一路碾压另一路时,融合收益递减、噪声反噬。
- **启示**:① 「加了融合就一定更好」是错觉,**必须用 eval 量化**——本项目 eval 正是推翻了"RRF 凭感觉加的有效"的假设;② 检索质量看 recall(能不能找到)更要看 MRR/recall@1(排第几),后者决定用户体验;③ 面试讲"我做了 eval 发现 RRF 在此数据集负优化,于是上 rerank"比"我加了 RRF 效果很好"有深度得多——诚实 + 数据驱动。

### 23. 删除 BM25:eval 证明独占命中=0,纯语义化(架构债清算)⚠️
- **现象**:eval 扩充精确关键词/代码/文件名 query 后,BM25 **独占命中=0**(35 条里没有一条是「BM25 找到、语义漏掉」),反而语义独占 8 条。BM25 既无独占召回,又拖累 MRR(踩坑 #22)。
- **根因**:bge-m3 对中文技术文档 + 专有名词的语义检索已**完全覆盖** BM25 能力边界;BM25 是纯负资产(拖 MRR + 增加建库成本 + 正是坑 #20 的 BM25 恢复超时元凶)。更深一层:**BM25 没被封装成独立模块**,而是作为 indexer 副产品散落 11 处(indexer 建/search 查/cli 装配/config/requirements/tests/...),这是「功能拆分而非模块封装」的技术债——增删改都是散弹枪修改。
- **修复**:删除 BM25 全链路——`indexer.py`(去 _rebuild_bm25/_save_bm25/bm25 property/load)、`search.py`(去 _keyword_rank/rrf_fuse,Searcher 纯语义)、`cli.py`(去 bm25_dir 注入)、`requirements.txt`(删 bm25s/jieba)、`tests/`(删 BM25 专测 + 同步构造签名)、`eval` 简化为纯语义监控、删 `diagnose_rrf.py`。83 tests 全绿,纯语义 recall@5=97.1%/MRR=0.718(与删前语义列一致,零损失)。
- **启示**:① **eval 不是摆设**——它把「BM25 该不该留」从争论变成数据结论(独占=0),用数据决策而非直觉;② **第三方能力必须封装成独立模块**(单一职责 + 清晰接口),不能寄生在业务流程里,否则像 BM25 这样散落 11 处,删一次伤筋动骨;③ **删除是消除债的机会**——删掉 BM25 后检索纯单路,不再有两路对齐/id_map 跨模块耦合,架构更干净,还顺带修了坑 #20 超时;④ 面试叙事:「我用 eval 发现 BM25 独占命中=0,但没有贸然删——先扩充数据集验证它在精确 query 上有无价值,确认无后才删,顺带修了一个启动超时 bug」——数据决策 + 识别直觉局限,比技术栈堆砌有说服力。

### 24. FlagEmbedding + transformers 5.x 不兼容(prepare_for_model 移除)
- **现象**:rerank eval 报 `XLMRobertaTokenizer has no attribute prepare_for_model`,FlagReranker.compute_score 崩。
- **根因**:`pip install FlagEmbedding` 拉了最新 transformers 5.14.1;transformers 5.x 大版本升级**移除了** `tokenizer.prepare_for_model`,而 FlagEmbedding 1.4.0 仍调用它 → AttributeError。
- **修复**:`pip install "transformers<5"` 降到 4.57.6(prepare_for_model 在 4.x 仍在)。requirements 已 pin `transformers<5` 防复发。
- **启示**:① 第三方 ML 库(FlagEmbedding / sentence-transformers / peft)对 transformers 大版本**强敏感**,装时不能盲装最新——`pip install X` 会连带拉最新 transformers,常踩 5.x 不兼容;② 依赖 ML 库时 requirements 应 pin transformers 上界(`<5`);③ 报 `X has no attribute Y`(X 是第三方库类)时,先查版本兼容,别怀疑自己代码。

### 25. qwen3 `/no_think`(prompt) 对 ollama 无效,必须 API `think:false` ⚠️
- **现象**:用 qwen3:8b 做意图分类,prompt 加 `/no_think` 仍 **14.5s/query**;改用 ollama API 的 `think:false` 参数后 **0.6s**——速度差 24 倍。
- **根因**:qwen3 的 `/no_think` 是**对话指令**(写在 prompt 里),但 **ollama 默认仍开 thinking**(qwen3 的推理模式),prompt 级指令**关不掉引擎级**的 thinking → 模型仍生成大量思考 token → 慢。必须用 ollama API 层的 `think: false`(传给 `/api/generate` 或 `/api/chat`)才真关。
- **修复**:ollama API 调用加 `"think": false`(`{"model":"qwen3:8b","prompt":"...","stream":false,"think":false}`)。
- **启示**:① qwen3 + ollama 关 thinking 是**引擎层开关**,不是 prompt 指令——`/no_think` 无效是隐藏坑,很多人踩;② **简单任务(分类/判断/抽取)关 thinking 大幅提速**(14.5s→0.6s),复杂推理才保留;③ 测模型速度前先确认 thinking 状态,否则误判"模型慢"(其实是 thinking 拖累);④ 项目其他 qwen3:8b 调用(工具循环中间判断、简单回答)加 `think:false` 也能整体提速——这是后续性能优化点。

### 26. notes-mcp 子进程启动阻塞致 MCP initialize 超时(坑#20 复发,4 层根因)⚠️
- **现象**:加 rerank 后后端启动报 MCP initialize 20s 超时(坑#20 同款),即使预建库 + request-timeout:120s(该配置不控制 initialize)。
- **根因**(逐层剥,4 层):
  1. **reranker 急加载** 2.2GB 阻塞 notes-mcp lifespan → 改懒加载(`_ensure_loaded`)
  2. 懒加载后仍超时:`reranker.py` 模块级 `from FlagEmbedding import FlagReranker` **触发 torch 加载(~5-10s)** → 延迟 import(移到 `_ensure_loaded` 内)
  3. 延迟 import 后仍超时:`NotesMcpBackendApplication.main()` 用 `Path.of("settings.json")` 相对 cwd(`web/backend`),**读不到项目根 settings.json** → 默认旧笔记路径(`笔记`)→ 笔记目录已改名(`AI笔记`)不存在 → notes-mcp 启动失败 → MCP 等不到 → 改 `findSettingsFile()` 向上查找
  4. 路径修后启动成功,但 IntentFilter prompt 太严(闲聊"你好"判 irrelevant)→ 调 prompt(闲聊/问候归 normal)
- **修复**:reranker 懒加载 + FlagEmbedding 延迟 import + main() 向上找 settings.json + IntentFilter prompt 调。
- **启示**:① 跨进程子进程启动慢要**逐层排查**(模型加载/import 开销/配置读取),别只看表面超时;② **重依赖(torch/transformers)的 import 本身就慢**(5-10s),放模块级阻塞启动,延迟到首次使用;③ 配置文件路径**不能依赖 cwd**(mvn run 的 cwd 是模块目录),向上查找或绝对化;④ MCP initialize 超时是**症状**,真因在子进程(notes-mcp)启动失败/慢——先抓子进程 STDERR;⑤ `request-timeout` 不控制 initialize(Spring AI 未暴露 MCP SDK 的 init timeout),靠子进程够快绕过。
